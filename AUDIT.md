# Audit of the original `index.html`

Method: read the whole original file first, then **ran** it (a Node simulation of its question bank and
selection logic for every secret, plus a real Chromium session on the original page) before changing anything.
Each finding is tagged:

- **[ran]** observed by executing the original
- **[code]** established by reading the source (not separately executed)

## What was already correct

- **[ran]** With truthful answers the original identified every secret in 1–50, 1–100, 1–250 and 1–1000
  (0 failures, max 7 / 8 / 9 / 12 questions). Guarantee 1 (never remove the secret under truthful answers) held.
  The weaknesses were elsewhere.

## Logic flaws found

| # | Flaw | Evidence | Requirement hit |
|---|------|----------|-----------------|
| 1 | **Disguised cutoff / direct questions.** `twoDigits` and `threeDigits` are range tests in disguise (10–99, 100–999). In range 1–100, `threeDigits` has exactly one yes-number, so it is literally "is it 100?". `digitSumOver10` / `digitSumUnder5` are also threshold questions. | **[ran]** yes-sets measured: `twoDigits` = 90 numbers (one unbroken stretch), `threeDigits` = 1 number (range 100) / 900 (range 1000) | Never ask direct or higher/lower questions |
| 2 | **Accidental "Not quite" is unrecoverable.** Rejecting the only candidate sets `finished = true`, leaves the guess box on screen, says "Time for my guess." and offers no undo, restore or correction. | **[ran]** after the click: headline unchanged, guess box still visible, no undo/restore control (0 found) | Rejected-guess undo; no-candidates recovery |
| 3 | **False success after a rejection.** In that dead state "That's it!" still works and announces *"Mind read! The computer guessed your number: 58."* | **[ran]** | Announce success only when justified |
| 4 | **Rejection is permanent and invisible.** `excluded` is never shown and never restorable; if the click was a mistake, every later count is silently wrong. | **[code]** | Correct counts; recovery |
| 5 | **Dead / misleading "best guess" branch.** `makeGuess` contains text for "I have N possibilities left, so this is my best guess", i.e. the code was written to allow a guess among several candidates, which the guarantees forbid. It is unreachable today only because of a guard in `askNext`. | **[code]** | Never present a guess as deduction |
| 6 | **Contradiction has no explanation or fix.** It says to "use Review answers", but that panel is hidden, the repair choice is a `<select>` plus three buttons, and nothing says *which* answer is probably wrong. | **[code]** + **[ran]** (Review button does nothing before a round starts) | No-candidates explanation and correction controls |
| 7 | **Row counts computed two different ways.** `answer()` stores the live candidate count (which excludes rejected guesses), while `correctAnswer()` recomputes each row from the answers alone (ignoring rejected guesses), so after a correction a row can disagree with the live count. | **[code]** | Accurate displayed counts |
| 8 | **"Not sure" is only text.** It is recorded in the list as plain text; the question is consumed with no visual distinction, no count of uncertain answers, and no way to ask it again. | **[code]** | "Not sure" visibly recorded |
| 9 | **Dead end when questions run out.** Answering Not sure to everything ends at "I need one more useful clue" after 264 clicks with nothing to click except Start over; there is no adaptive generation. | **[ran]** | Adaptive questions; clear "cannot distinguish" message |
| 10 | **Changing the range mid-round silently abandons it** (no confirmation); old history rows stay in the DOM. | **[ran]** (rows left over) | Usability |
| 11 | **"Question style" did nothing mathematical.** Both options asked the same kind of question; only tie-breaking differed. | **[code]** | Clear instructions |
| 12 | **Selection ignores simplicity and is unseeded.** Random choice among "near-best" questions made results non-reproducible and untestable. | **[code]** | Deterministic tie-breaking in tests |
| 13 | **Unsafe pattern.** `renderHistory` builds HTML strings and an inline `onclick` with data interpolated into `innerHTML`. Today the data is internal strings, so it is not exploitable, but it is the pattern to avoid. | **[code]** | Avoid unsafe HTML interpolation |
| 14 | **No explicit focus styling; instructions hidden behind a button.** | **[ran]** computed outline on the focused Start button: `auto 0px` (browser default only) | Keyboard focus; clear instructions |
| 15 | **No tests, one monolithic script.** Question generation, filtering, selection, state and UI were interleaved in one `<script>`. | **[code]** | Separation of concerns; automated tests |

## Fixes (summary; see CHANGELOG.md)

1. Questions are generated by `js/questions.js` and **every** question must pass structural guards over the full
   range: at least 3 numbers on each side and at least 3 separate stretches per side. This makes a direct check or
   cutoff impossible by construction, and `twoDigits` / `threeDigits` / digit-sum thresholds were removed.
2. A single pure state machine (`js/game.js`) derives everything from *answers + rejected numbers + confirmation*.
   The computer reaches the guess phase **only** when exactly one candidate remains.
3. Undo stack, per-row Yes / No / Not sure correction, restorable rejections, and single-change repair suggestions
   for contradictions (all repairs reachable, none hidden).
4. Adaptive generation of extra residue / digit-sum questions, and an honest "stuck" state that refuses to guess.
5. Accessible, responsive UI built with `createElement` / `textContent` only.
6. Automated tests: 101 Node logic checks and 135 real-browser checks (results in `tests/`).

## Defects found *by the new tests* while building the fix

These were real bugs in my first draft of the rewrite, caught by the browser suite and fixed:

- The page moved focus to the Start button on load, bypassing the skip link and instructions for keyboard and
  screen-reader users.
- The contradiction panel capped repairs at six and sorted newest-first, so the repair for an early mistaken answer
  could be hidden even though the engine had computed it.

# Addendum — Division Calculator (2.1.0)

A convenience panel was added. It was audited against the same standard as the rest of the project.

**Integration point.** The layout was one column (`.app` → header, game card, footer). The panel was added as a sibling
`<aside>` after the game card, so it is last in Tab order and falls below the game on narrow screens. Its logic is in
`js/calculator.js` and its wiring in `js/calculator-ui.js`; neither can see the game.

**Isolation evidence (all executed):**
- `questions.js`, `engine.js`, `game.js` are **byte-identical** to the audited 2.0.0 files (sha256 checked; a test now fails if they change).
- `ui.js` changed by **one line**: the Y / N / S shortcut handler returns early when the event comes from inside `#calcPanel`.
  Without it, pressing Y with the Clear button focused would have answered the game; a browser test proves it no longer does.
- The calculator files contain no reference to the game, engine, questions, candidates or the debug hook (static test),
  contain no keyboard listeners, and address only elements whose ids start with `calc`.
- Browser test: with a round in progress, typing, clearing and entering invalid/boundary values in the calculator left the game's
  state (candidates, history, undo, question, phase) and its visible text **identical**, and game answers did not change the calculator.
- The panel text contains only calculator content (it cannot reveal the secret, candidates or internal answers).

**Visual regression check (one-off, not shipped).** Computed styles of 18 game elements × 16 properties at 8 viewport widths
(2,304 comparisons) were compared between 2.0.0 and 2.1.0: the only differences were `min-height: 0px → auto` on grid
items, with identical rendered sizes. The game card keeps its size at every width; its position is unchanged at ≥ 1360 px and
≤ 1059 px and shifts 135 px left between 1060–1359 px to make room for the panel.

**Test changes (disclosed).** Two existing assertions stated "the page has no `<input>`" (logic suite: static scan;
browser suite: load check). Their intent is that there is nowhere to type the secret; they now require *no input in the game
area* and exactly two inputs, both inside the calculator panel. No other existing assertion was altered.

**Defects found by the new tests while building the feature (all in test code, none in shipped code):**
a "forbidden token" scan that flagged the legitimate word "undefined" in the zero-divisor message; a substring match that
caught the unrelated word "Recalculated" in `ui.js`; a checker that crashed on `NaN` instead of reporting it (found by a
negative control); and a case-sensitive text comparison against CSS-uppercased labels.
